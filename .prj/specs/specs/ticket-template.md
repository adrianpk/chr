# Ticket Template

Status: initial

Source quiz: `.prj/quizzes/curated/ticket-template-model-quiz.md`
Model: `.prj/specs/specs/ticket-template-model.md`

## Purpose

Define the initial Markdown ticket format generated and managed by `chr`.

The format must be readable as a normal file, versionable in git, and structured enough for later CLI operations such as listing, filtering, status updates, and ticket execution loops.

## Storage

Tickets live under `.chr/tickets/`.

Ticket paths must not encode status. Status lives in ticket metadata only. Duplicating status in both path and metadata would require reconciliation and would be error-prone for both humans and agents.

Ticket storage should support use-case-oriented nesting from the beginning, because large projects may eventually contain hundreds of ticket files.

Project-wise tickets are represented by an empty or absent `use_case`. They should not be forced into a synthetic use case.

The exact path shape for project-wise tickets and use-case tickets remains open for the implementation slice.

## Filename

Ticket filenames use `key-truncated-name`.

Example:

```text
PRJ001-Do-something.md
```

The filename should contain only enough text to make directory listings readable. Full title and structured metadata remain inside the ticket file.

## Metadata

Tickets use YAML frontmatter for machine-readable metadata.

Metadata keys use `snake_case`.

Initial metadata shape:

```yaml
---
key:
title:
status: open
priority:
severity:
type:
tags: []
use_case:
project_area:
created_at:
updated_at:
---
```

`key`, `created_at`, and `updated_at` are generated by `chr`. Users should not need to provide them manually when creating a ticket.

`tags` is the initial free-form grouping field. The initial model does not include a separate `labels` field.

## Body

Generated tickets should be compact. Headings are enough; the template should not force ceremony at creation time.

Initial body shape:

```md
# Description

# Checklist

# Acceptance

# Comments

# Blocker

# Validation
```

`Description` explains the work to be done.

`Checklist` tracks execution steps. It is optional and may be updated by an agent while working.

`Acceptance` defines the functional or behavioral conditions required for the ticket to be accepted.

`Comments` is an append-only area for feedback, iteration notes, and coordination. Comments remain in the ticket file for the initial version.

`Blocker` records blocking context when the ticket cannot continue.

`Validation` records checks, commands, tests, or review evidence.

## Key Generation

Initial keys use this shape:

```text
CHR-<number>
```

The prefix is configurable in `.chr/config.yml`.

The initial counter may be derived from existing ticket files. SQLite may later provide an indexed or modeled source for key generation, but SQLite is not required for the first ticket template implementation.

## Status Flow

Initial status values:

```text
open
ready
in_progress
reviewing
blocked
solved
merged
closed
```

`solved` remains a valid status.

`merged` means the change was integrated.

`closed` is not equivalent to solved; a ticket may be closed without being considered solved.

The final transition rules remain open for the implementation slice.

## Classification Values

Initial priority values:

```text
low
normal
high
critical
```

Initial severity values:

```text
low
normal
high
critical
```

Initial type values:

```text
task
bug
feature
cleanup
research
docs
```

These sets should remain easy to iterate after real project usage.
