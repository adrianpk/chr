# Ticket Template Model Quiz Raw

Status: closed

## Q1: Metadata Format

Question: Should the initial ticket template use YAML frontmatter for metadata?

Answer: Yes. YAML frontmatter sounds reasonable because it gives `chc` structured fields to parse later for list, status, and loop behavior.

## Q2: Required Fields

Question: Which fields should be required from the beginning?

Answer:

- `key` should exist, but it must be generated by `chc`, not manually supplied by the user.
- `created_at` and `updated_at` should exist and be editable in the file, but `chc` should generate and update them. The user should not have to provide them just to create a ticket.
- The ticket needs a clear description area for what should be done.
- The ticket should include an optional Markdown checklist that the agent can use to mark progress.

## Q3: Key Format

Question: Should keys use `CHC-<number>` with configurable prefix?

Answer: Yes. Use `CHC-<number>` initially. The prefix should be configurable in `.chc/config.yml`. The counter can initially be derived from existing tickets and later from SQLite if that becomes part of the model.

## Q4: Status Values

Question: Should initial status values be `open`, `ready`, `in_progress`, `reviewing`, `blocked`, `solved`, and `closed`?

Answer: Replicate the known status flow, but include `merged`. It may replace `solved` or come after it. The distinction matters because one actor may resolve a ticket, another may review it, and another may merge it.

## Q5: Solved, Merged, and Closed

Question: Should `solved`, `merged`, and `closed` be separate states?

Answer: Keep `solved` as an option. A ticket can also be closed without being considered solved.

## Q6: Priority Values

Question: Which initial priority values should ship?

Answer: Start with basic values and iterate later. The first set should be simple; later we can remove values if there are too many or add more if needed.

## Q7: Severity Values

Question: Should severity use the same basic iterable criterion?

Answer: Use the same criterion as priority. Start basic, then iterate as real usage shows whether values should be removed or added.

## Q8: Type Values

Question: Should the initial type values be `task`, `bug`, `feature`, `cleanup`, `research`, and `docs`?

Answer: Yes, that initial set is fine.

## Q9: Use Case and Project Area

Question: Should `use_case` and `project_area` both exist in initial ticket metadata?

Answer: Yes. `use_case` defines a set of things associated with a feature or flow. `project_area` can be more transversal, such as `uxui` or `persistence`. There is some discomfort with underscores in property names; the naming convention should be decided explicitly.

## Q10: Metadata Naming

Question: Should metadata keys use `snake_case`, with free slug-like string values where applicable?

Answer: Yes. The mapping advantage for code is enough to accept `snake_case` for metadata keys.

## Q11: Tags and Labels

Question: Should `tags` and `labels` be distinct concepts, or should the initial model use only one of them?

Answer: Use only `tags` initially. The terms were used almost as synonyms, and duplicating both fields would add unnecessary vocabulary at this stage.

## Q12: Acceptance, Validation, and Execution Checklist

Question: Should the template separate `Acceptance` and `Validation`, or is one section enough?

Answer: Keep them separate, and also keep the execution checklist as its own concept. The task checklist tracks what must be executed while working on the ticket. Acceptance criteria describe the functional or behavioral conditions the ticket must satisfy to be accepted. Validation records the checks, commands, tests, or review evidence used to prove the result.

## Q13: Ticket Weight

Question: Does keeping comments plus checklist, acceptance, and validation make the initial ticket too heavy?

Answer: Keep the sections together in the initial ticket file, but make the generated template compact. The sections should exist as headings without forcing users to fill all of them when creating a ticket.

## Q14: Ticket Location

Question: Where should tickets live inside `.chc/`?

Answer: Use-case-oriented nesting should be considered from the beginning. This is not nesting for its own sake; it keeps the ticket tree readable when a project eventually has hundreds of ticket files. A flat `.chc/tickets/` directory may become noisy too quickly.

## Q15: Status in Path

Question: Should ticket paths include status directories?

Answer: No. Even if agents can manage file moves, status directories duplicate metadata already stored in the ticket file. That creates reconciliation problems for humans and agents. If a conflict exists, the internal metadata would need priority, but that is error-prone and would require monitoring before each task.

## Q16: Use Case Requirement

Question: Should `use_case` be required when creating a ticket?

Answer: No. Some tickets are project-wise tasks, especially near the beginning of a project, and should not be forced into a use case.

## Q17: Project-Wise Ticket Category

Question: Should project-wise tickets have an explicit path category?

Answer: Not necessarily. An empty or absent `use_case` already represents a project-wise ticket. A separate explicit category may not be needed.

## Q18: Ticket Filename

Question: Should the filename include only key plus a truncated name?

Answer: Use `key-truncated-name`, for example `PRJ001-Do-something.md`.
