# Ticket Template Model Quiz

Status: closed

Spec: `.prj/specs/specs/ticket-template.md`
Model: `.prj/specs/specs/ticket-template-model.md`

## Purpose

Define the initial file-based ticket template model for Chryso.

## Decisions

- Tickets use YAML frontmatter for machine-readable metadata.
- Ticket keys are generated by `chr`; users should not need to provide them manually.
- Initial key shape is `CHR-<number>`.
- The key prefix is configurable in `.chr/config.yml`.
- The initial counter may be derived from existing ticket files.
- SQLite may later provide an indexed or modeled source for key generation, but it is not required for the first template.
- `created_at` and `updated_at` are present in metadata and generated by `chr`.
- Timestamp fields remain editable in files, but they should not create manual ceremony for users.
- Tickets need a clear `Description` section for the work to be done.
- Tickets include an optional Markdown checklist for agent-visible progress tracking.
- The status flow should include a merged state, because resolving, reviewing, and merging can be separate responsibilities.
- `solved` remains a valid status option.
- `merged` means the change was integrated.
- `closed` is not equivalent to solved; a ticket may be closed without being considered solved.
- Priority should start with a basic set and remain easy to iterate.
- Severity should follow the same basic, iterable approach as priority.
- Initial type values are `task`, `bug`, `feature`, `cleanup`, `research`, and `docs`.
- `use_case` and `project_area` should both exist in initial metadata.
- `use_case` groups work by feature or user flow.
- `project_area` groups work by transversal concern or technical area, such as `uxui` or `persistence`.
- Metadata keys should use `snake_case`.
- Metadata values can be free strings or slug-like values where appropriate.
- Use `tags` as the initial free-form grouping field.
- Do not introduce a separate `labels` field in the initial ticket model.
- Keep the execution checklist, acceptance criteria, and validation evidence as separate sections.
- The checklist tracks work execution.
- Acceptance criteria define what the ticket must satisfy to be accepted.
- Validation records checks, commands, tests, or review evidence.
- Comments should remain in the same ticket file for the initial version.
- The generated ticket should stay compact: headings are enough, and sections should not force ceremony at creation time.
- Ticket storage should consider use-case-oriented nesting from the beginning to avoid an unreadable flat directory when projects accumulate many tickets.
- Ticket paths should not include status directories.
- Ticket status should live in ticket metadata only.
- Avoid duplicating status in both path and metadata, because reconciliation would be error-prone.
- `use_case` should not be required for every ticket.
- Some tickets are project-wise tasks, especially early in a project, and should not be forced into a use case.
- An empty or absent `use_case` represents a project-wise ticket.
- A separate project-wise path category is not clearly needed.
- Ticket filenames should use `key-truncated-name`.
- Example filename: `PRJ001-Do-something.md`.
