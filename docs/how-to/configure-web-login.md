# Configure Single-user Web Login

Configure one account for the Web servers run by your local operating-system
user. There is no browser registration or account administration page.

## Create the Account

Run this in an interactive terminal:

```sh
chr web login setup --username operator
```

Enter and confirm a password of 12-1024 bytes. Entry is masked. The password is
not accepted as a command-line argument or printed. Setup stores only a salted
password verifier in `web-login.json` under the resolved user configuration
directory, normally `~/.config/chr/`. The file is private, with mode `0600`;
it is not a project artifact. Development environments use their own resolved
configuration directory.

Setup does not start or restart a server. Restart existing Web servers after
setup. Start a protected LAN instance with:

```sh
chr web serve --allow-lan --require-login
```

Open the server's reachable address normally. Log in once and use links,
refreshes, dialogs and forms without URL tokens. The requested page opens
after login.

`--require-login` refuses startup when no account exists. A configured account
is loaded automatically even without that flag, on loopback and LAN binds.
Malformed, linked or publicly readable credential files refuse startup; they
never silently disable authentication. Preview the effective policy with
`chr web serve --allow-lan --require-login --dry-run`.

The configured login replaces the legacy Web token check; a bearer header or
query token cannot bypass it. Without a configured account, existing local,
explicit trusted-LAN and legacy token modes retain their behavior.

## Sessions and Logout

Pages, direct document URLs, fragments and actions require an active session.
Only embedded static assets and the data-free `/healthz` endpoint are public.
An expired HTMX request returns the browser to the full login page.

Sessions last 12 hours from login. They use a host-only, HTTP-only,
`SameSite=Strict` cookie and server-side state. Logout revokes that session
immediately; restarting the server invalidates every session. Logging in again
replaces the browser's previous session. Up to 32 sessions can exist for the
same account, allowing a computer and phone to use it. At capacity, a new login
revokes an existing session.

The server permits five login attempts per minute across all clients. This
bounds password verification work without trusting proxy-supplied client
addresses. Writes, login and logout require the actual same origin; broad
allowed-origin settings cannot grant cookie-authenticated cross-origin writes.

Network exposure still follows the [Web exposure policy](expose-local-web-ui.md).
HTTP login is intended for the existing trusted internal-network use case.
Cookies use `Secure` when the HTTP handler receives TLS directly. Forwarded
headers do not establish a trusted TLS boundary or change the login origin.
Login adds no TLS listener or proxy trust configuration.

## Change the Account or Password

```sh
chr web login setup --username operator --replace
```

Restart every running Web server afterward to load the new verifier and revoke
old sessions. Account setup refuses replacement without `--replace`. There is
no unauthenticated browser password-reset flow.

The verifier uses PBKDF2-HMAC-SHA-256 with a random 16-byte salt, 600,000
iterations and a 32-byte output, using Go's standard library. The work factor
follows the [OWASP password-storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
Session identifiers are generated by the operating-system random source;
only their hashes remain in server memory.
