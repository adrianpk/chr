# Commands

This page lists the main command surfaces. Use `chc --help` and command-specific
help for exact flags.

Running `chc` without a subcommand opens the TUI for the resolved project.

## Workspace

Initialize a managed project:

```sh
chc init
```

Preview initialization:

```sh
chc init --dry-run
```

## TUI

Open the local operational console:

```sh
chc
chc tui
chc tui --dir /path/to/project
```

See [TUI reference](tui.md) for views, keybindings, command palette behavior,
and confirmation modes.

See [CLI TUI action matrix](cli-tui-action-matrix.md) for current parity
between command-line and interactive operations.

## Runtime

Install missing runtime defaults:

```sh
chc runtime init
```

Validate the runtime boundary:

```sh
chc runtime validate
```

Preview validation:

```sh
chc runtime validate --dry-run
```

## Dev To Main Gate

Collect promotion evidence for a `dev` to `main` alignment:

```sh
chc gate dev-main --base origin/main --head HEAD
```

The gate collects Git range evidence, runs the configured validation command,
classifies ChrysoCoord-managed work versus manual or external changes, and
writes Markdown and JSON reports under `.chc/user/reports/gates/`.

Initialize a Woodpecker gate workflow:

```sh
chc gate woodpecker init
```

Preview the generated workflow without writing `.woodpecker.yml`:

```sh
chc gate woodpecker init --dry-run
```

Update an existing ChrysoCoord-generated Woodpecker workflow:

```sh
chc gate woodpecker init --write
```

Existing `.woodpecker.yml` files are not modified unless they contain the
ChrysoCoord marker generated by this command.

See [Dev to main gate](dev-main-gate.md) for the config and report contract.

## Projects

Register and select local projects:

```sh
chc project add /path/to/project
chc project select /path/to/project
chc project current
chc project list
```

## Project and Use-Case Metadata

Save project metadata:

```sh
chc metadata project set \
  --name "Billing Service" \
  --description "Coordinates billing workflows." \
  --context "Project-wide context."
```

Create or update use-case metadata:

```sh
chc metadata case set billing \
  --name "Billing Sync" \
  --description "Synchronize billing records." \
  --context "Use-case context."
```

The metadata commands write the same Markdown files edited by the TUI Project
and Cases views.

## Dumps

List, create, inspect, and edit dumps:

```sh
chc dump list
chc dump new --title "Billing notes" --content "Initial context."
chc dump new --title "Billing notes" --content "Use-case context." --use-case billing
chc dump show .chc/user/dumps/billing-notes.md
chc dump save .chc/user/dumps/billing-notes.md --content "# Billing notes"
chc dump append .chc/user/dumps/billing-notes.md --content "Additional context."
chc dump open .chc/user/dumps/billing-notes.md
```

Dump paths are project-relative and must stay under `.chc/user/dumps/`.
`chc dump new` writes a curated primary dump and a `-raw.md` sibling. Listing
dumps returns the curated primary documents; raw siblings are retained as source
captures and are not selected as regular dump context.

## Runtime Quizzes

Run bounded quiz sessions against project or use-case context:

```sh
chc quiz list
chc quiz start --use-case billing --mode deep
chc quiz resume --use-case billing
chc quiz answer --use-case billing --answer "Retries must be idempotent."
chc quiz skip --use-case billing
chc quiz complete --use-case billing
chc quiz cancel --use-case billing
chc quiz mode fast --use-case billing
```

These commands operate on the same runtime quiz state shown in the TUI Quizzes
view. They are separate from `chc author quiz new`.

## Specs

List and generate specs:

```sh
chc spec list
chc spec generate --use-case billing
```

Spec generation reads accumulated project and use-case material, including
metadata, context, dumps, quizzes, and related workspace documents.

## Plans

List, generate, regenerate, and materialize plan tracking:

```sh
chc plan list
chc plan generate --use-case billing
chc plan regenerate --use-case billing
chc plan tracking create --use-case billing
```

`plan generate` does not overwrite an existing generated plan. Use
`plan regenerate` when the generated plan should be archived and replaced.
`plan tracking create` requires an existing plan and creates the tracking
Markdown document plus one ticket per generated slice.

## Tickets

Create and inspect tickets:

```sh
chc ticket new "Add completed task support" \
  --synopsis "Add task completion support." \
  --type feature \
  --priority high
chc ticket list
chc ticket show CHC-1
chc ticket board
```

`chc ticket board` prints Board totals, normal Board columns, and tickets in
each column for the resolved project.

Update ticket state:

```sh
chc ticket comment CHC-1 "Validation fails in the completion path."
chc ticket status CHC-1 ready
chc ticket status CHC-1 in_progress
chc ticket status CHC-1 reviewing
```

Ticket creation requires a synopsis. The synopsis is short searchable metadata
used by Board and detail views.

Start one ticket:

```sh
chc ticket start CHC-1
```

Preview one ticket execution:

```sh
chc ticket start CHC-1 --dry-run
```

Apply an execution result:

```sh
chc ticket apply-result <execution-id>
```

Run a filtered foreground loop:

```sh
chc ticket loop --status ready_for_dev --priority high --max-iterations 3
```

Preview loop selection:

```sh
chc ticket loop --dry-run
```

## Agent Work

Run agent work for one ticket:

```sh
chc work ticket CHC-1
```

Run agent work for all ready tickets:

```sh
chc work run-all
```

Preview the ready-ticket queue without execution:

```sh
chc work run-all --dry-run
```

Run or preview a filtered ready-ticket queue:

```sh
chc work run-all --priority high --order priority
chc work run-all --dry-run --tag backend --order priority_severity
```

`work run-all` uses the shared agent-work selection contract. Defaults are
`ready_for_dev` tickets, oldest first by `created_at`. Supported filters mirror
`chc ticket loop`: `--status`, `--priority`, `--severity`, `--project-area`,
`--tag`, `--type`, `--use-case`, and `--order`.

## QA Scenarios

Reset a QA scenario from its versioned reference copy:

```sh
make qa-reset QA_CASE=blog QA_REF=001
make qa-reset-blog
```

Run the active scenario tests:

```sh
make qa-test QA_CASE=blog
make qa-test-blog
```

Run scenario smoke validation:

```sh
make qa-smoke QA_CASE=blog QA_REF=001
make qa-smoke-blog
```

QA references live under `qa/ref/<ref>/<case>`. Active project copies live
under ignored `qa/project/<case>` directories, and previous active copies are
moved to ignored `qa/tmp/<case>` directories during reset.

## Authoring

Create an authoring session:

```sh
chc author session new --target spec --topic "Billing sync"
```

Generate a context-aware quiz:

```sh
chc author quiz new --target spec --topic "Billing sync"
```

Generate or edit a spec with `status: draft` when quiz answers still need
review. Legacy `quiz-to-draft` exists only for compatibility with older
authoring sessions.

Run the current assisted authoring flow:

```sh
chc author assisted start --target spec --topic "Billing sync"
chc author assisted resume --session <session-handle>
chc author assisted answer --session <session-handle> --turn <turn-id> --answer "Retry writes must be idempotent."
chc author assisted status --session <session-handle>
chc author assisted finalize --session <session-handle> --target-kind spec --target-name "billing sync spec"
```

The current assisted commands use explicit adapter inputs for deterministic
local behavior.

The legacy quiz-to-draft command remains available for older authoring sessions:

```sh
chc author promote quiz-to-draft --session <session-id> --quiz <quiz-path>
```

## Daemon

Run local foreground coordination:

```sh
chc daemon status
chc daemon start --max-iterations 1
chc daemon stop
```

## Notify

Inspect notification configuration:

```sh
chc notify status
```

Preview the Telegram setup-check payload:

```sh
chc notify telegram test --dry-run
```

Send the Telegram setup-check message:

```sh
chc notify telegram test
```

The dry-run command does not contact Telegram. Non-dry-run dispatch reads the
bot token from the configured environment variable and records a notification
audit event.

Preview Telegram update parsing from a fixture:

```sh
chc notify telegram poll --fixture updates.json --dry-run
```

Persist accepted and rejected remote command handoff records from a fixture:

```sh
chc notify telegram poll --fixture updates.json
```

## Proving

Run direct proving-ground workflows against controlled objectives:

```sh
chc proving validate --objective .chc/proving/objectives/TODO-1-fix-task-id-reuse.md
chc proving run --objective .chc/proving/objectives/TODO-1-fix-task-id-reuse.md --dry-run
chc proving ralph --objective .chc/proving/objectives/TODO-1-fix-task-id-reuse.md --max-attempts 3
```

Proving commands are for sandbox proofing and validation, not the normal ticket
execution path.
