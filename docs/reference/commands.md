# Commands

This page lists the main command surfaces. Use `chr --help` and command-specific
help for exact flags.

Running `chr` without a subcommand opens the TUI for the resolved project.

## Workspace

Initialize a managed project:

```sh
chr init
```

Preview initialization:

```sh
chr init --dry-run
```

## TUI

Open the local operational console:

```sh
chr
chr tui
chr tui --dir /path/to/project
```

See [TUI reference](tui.md) for views, keybindings, command palette behavior,
and confirmation modes.

See [CLI TUI action matrix](cli-tui-action-matrix.md) for current parity
between command-line and interactive operations.

## Web UI

Serve the optional local browser UI for the resolved project:

```sh
chr web serve
```

Preview the resolved Web UI config without listening on a socket:

```sh
chr web serve --dry-run
```

Serve another managed project:

```sh
chr web serve --dir /path/to/project
```

Override the bind address and port for this process:

```sh
chr web serve --host 127.0.0.1 --port 7331
```

Override token policy for this process:

```sh
chr web serve --require-token auto
chr web serve --require-token true
chr web serve --require-token false
```

`auto` requires token protection for non-loopback binds and keeps localhost
access token-free. `true` always requires a token. `false` disables token
protection and prints an exposure warning when the server is bound to a
non-loopback interface.

The Web UI does not start from `chr`, `chr tui`, or normal work commands. It
starts only from `chr web serve`.

See [Run the local Web UI](../how-to/run-local-web-ui.md), [Expose the local Web
UI deliberately](../how-to/expose-local-web-ui.md), and [Web UI action
matrix](web-ui-action-matrix.md).

## Dev To Main Gate

Collect promotion evidence for a `dev` to `main` alignment:

```sh
chr gate dev-main --base origin/main --head HEAD
```

The gate collects Git range evidence, runs the configured validation command,
classifies Chryso-managed work versus manual or external changes, and
writes Markdown and JSON reports under `.chr/user/reports/gates/`.

Initialize a Woodpecker gate workflow:

```sh
chr gate woodpecker init
```

Preview the generated workflow without writing `.woodpecker.yml`:

```sh
chr gate woodpecker init --dry-run
```

Update an existing Chryso-generated Woodpecker workflow:

```sh
chr gate woodpecker init --write
```

Existing `.woodpecker.yml` files are not modified unless they contain the
Chryso marker generated by this command.

See [Dev to main gate](dev-main-gate.md) for the config and report contract.

## Projects

Register and select local projects:

```sh
chr project add /path/to/project
chr project select /path/to/project
chr project current
chr project list
```

## Project and Use-Case Metadata

Save project metadata:

```sh
chr metadata project set \
  --name "Billing Service" \
  --description "Coordinates billing workflows." \
  --context "Project-wide context."
```

Create or update use-case metadata:

```sh
chr metadata case set billing \
  --name "Billing Sync" \
  --description "Synchronize billing records." \
  --context "Use-case context."
```

The metadata commands write the same Markdown files edited by the TUI Project
and Cases views.

## Dumps

List, create, inspect, and edit dumps:

```sh
chr dump list
chr dump new --title "Billing notes" --content "Initial context."
chr dump new --title "Billing notes" --content "Use-case context." --use-case billing
chr dump show .chr/user/dumps/billing-notes.md
chr dump save .chr/user/dumps/billing-notes.md --content "# Billing notes"
chr dump append .chr/user/dumps/billing-notes.md --content "Additional context."
chr dump open .chr/user/dumps/billing-notes.md
```

Dump paths are project-relative and must stay under `.chr/user/dumps/`.
`chr dump new` writes a curated primary dump and a `-raw.md` sibling. Listing
dumps returns the curated primary documents; raw siblings are retained as source
captures and are not selected as regular dump context.

## Runtime Quizzes

Run bounded quiz sessions against project or use-case context:

```sh
chr quiz list
chr quiz start --use-case billing --mode deep
chr quiz resume --use-case billing
chr quiz answer --use-case billing --answer "Retries must be idempotent."
chr quiz skip --use-case billing
chr quiz complete --use-case billing
chr quiz cancel --use-case billing
chr quiz mode fast --use-case billing
```

These commands operate on the same runtime quiz state shown in the TUI Quizzes
view. They are separate from `chr author quiz new`.

## Specs

List and generate specs:

```sh
chr spec list
chr spec generate --use-case billing
```

Spec generation reads accumulated project and use-case material, including
metadata, context, dumps, quizzes, and related workspace documents.

Spec generation writes the Markdown spec only.

## Acceptance Features

Generate an acceptance feature from an existing spec and related context:

```sh
chr acceptance feature generate --use-case billing
```

Generated features are written under:

```text
.chr/user/acceptance/<scope>.feature
```

If generation needs more scenario detail, Chryso writes feature-round notes
under:

```text
.chr/user/acceptance/<scope>-feature-round.md
```

Feature artifacts are written only when the generated Gherkin passes static
checks. If more scenario detail is needed, or the use case is not suitable for a
feature artifact, the command reports that status without writing a file. See
[Acceptance feature generation](acceptance-feature-generation.md).

When the command returns `needs_more_info`, it writes feature-round prompts when
the model provides them. Recording answers to those prompts is a separate manual
step in the current implementation.

## Plans

List, generate, regenerate, and materialize plan tracking:

```sh
chr plan list
chr plan generate --use-case billing
chr plan regenerate --use-case billing
chr plan tracking create --use-case billing
```

`plan generate` does not overwrite an existing generated plan. Use
`plan regenerate` when the generated plan should be archived and replaced.
`plan tracking create` requires an existing plan and creates the tracking
Markdown document plus one ticket per generated slice.

## Tickets

Create and inspect tickets:

```sh
chr ticket new "Add completed task support" \
  --synopsis "Add task completion support." \
  --type feature \
  --priority high
chr ticket list
chr ticket show CHR-1
chr ticket board
```

`chr ticket board` prints Board totals, normal Board columns, and tickets in
each column for the resolved project. Ticket rows include a final evidence
status cell. The cell is `-` when the ticket has no evidence strategy checklist;
otherwise it is `complete`, `incomplete`, `blocked`, or `malformed`.

`chr ticket list` prints the same compact evidence status as the final field.

`chr ticket show <key>` prints detailed evidence fields when the ticket contains
an anchored evidence strategy checklist:

```text
evidence: complete
evidence_strategy: complete done
evidence_gherkin: required done
evidence_tests: mixed done
evidence_validation: passed done
evidence_summary: complete done
```

Update ticket state:

```sh
chr ticket comment CHR-1 "Validation fails in the completion path."
chr ticket status CHR-1 ready
chr ticket status CHR-1 in_progress
chr ticket status CHR-1 reviewing
```

Inspect ticket review workflow mode:

```sh
chr ticket review-mode status
chr ticket review-mode status --dry-run
chr ticket review-mode diagnostics --url https://forge.example.test/owner/repo/pulls/123
chr ticket review-mode diagnostics --url https://github.com/owner/repo/pull/123 --dry-run
```

Ticket creation requires a synopsis. The synopsis is short searchable metadata
used by Board and detail views.

Start one ticket:

```sh
chr ticket start CHR-1
```

Preview one ticket execution:

```sh
chr ticket start CHR-1 --dry-run
```

Review a ticket that is ready for review:

```sh
chr ticket review CHR-1 --result pass
chr ticket review CHR-1 --result needs_changes --finding "Handle the nil input path."
```

See [Ticket review workflow](ticket-review-workflow.md) for review state
transitions, pull request references, and repair handoff behavior.

Merge a reviewed ticket that is ready for merge:

```sh
chr ticket merge CHR-1
chr ticket merge CHR-1 --dry-run
chr ticket merge CHR-1 --base develop --strategy rebase
```

See [Ticket merge workflow](ticket-merge-workflow.md) for merge preflight,
provider execution, and merge metadata behavior.

Apply an execution result:

```sh
chr ticket apply-result <execution-id>
```

Run a filtered foreground loop:

```sh
chr ticket loop --status ready_for_dev --priority high --max-iterations 3
```

Preview loop selection:

```sh
chr ticket loop --dry-run
```

## Agent Work

Inspect readiness before starting agent work:

```sh
chr work doctor
```

Apply safe readiness repairs and print the resulting report:

```sh
chr work doctor --fix-safe
```

Run agent work for one ticket:

```sh
chr work ticket CHR-1
```

Run agent work for all ready tickets:

```sh
chr work run-all
```

Preview the ready-ticket queue without execution:

```sh
chr work run-all --dry-run
```

Run or preview a filtered ready-ticket queue:

```sh
chr work run-all --priority high --order priority
chr work run-all --dry-run --tag backend --order priority_severity
```

`work run-all` uses the shared agent-work selection contract. Defaults are
`ready_for_dev` tickets, oldest first by `created_at`. Supported filters mirror
`chr ticket loop`: `--status`, `--priority`, `--severity`, `--project-area`,
`--tag`, `--type`, `--use-case`, and `--order`.

In serialized integration modes, `work run-all` completes the current ticket's
development, review policy, repair when applicable, and merge or block before
selecting the next normal ticket.

Readiness behavior is documented in [Work readiness](work-readiness.md).

Locate runtime artifacts for one execution:

```sh
chr work logs exec-1
```

Dash and agent event streams may also point directly to `ticket_path`,
`execution_report_path`, `runtime_log_path`, and `validation_log_path`.

Summarize an event stream for recovery or diagnostics:

```sh
chr work events ops/default/run/<execution-artifact-id>/evidence/events.jsonl
chr work events ops/default/run/<loop-artifact-id>/evidence/events.jsonl
```

Event streams, runtime logs, reports, and Dash rendering are documented in
[Agent work observability](agent-work-observability.md).

## QA Scenarios

Reset a QA scenario from its versioned reference copy:

```sh
make qa-reset QA_CASE=blog QA_REF=001
make qa-reset-blog
make qa-reset-tictactoe
```

Run the active scenario tests:

```sh
make qa-test QA_CASE=blog
make qa-test-blog
make qa-test-tictactoe
```

Run scenario smoke validation:

```sh
make qa-smoke QA_CASE=blog QA_REF=001
make qa-smoke-blog
make qa-smoke-tictactoe
```

QA references live under `qa/ref/<ref>/<case>`. Active project copies live
under ignored `qa/project/<case>` directories, and previous active copies are
moved to ignored `qa/tmp/<case>` directories during reset.

The `blog` smoke check expects the seeded unknown-post failure. Other smoke
checks expect the reset project to pass its baseline tests.

## Authoring

Create an authoring session:

```sh
chr author session new --target spec --topic "Billing sync"
```

Generate a context-aware quiz:

```sh
chr author quiz new --target spec --topic "Billing sync"
```

Generate or edit a spec with `status: draft` when quiz answers still need
review. Legacy `quiz-to-draft` exists only for compatibility with older
authoring sessions.

Run the current assisted authoring flow:

```sh
chr author assisted start --target spec --topic "Billing sync"
chr author assisted resume --session <session-handle>
chr author assisted answer --session <session-handle> --turn <turn-id> --answer "Retry writes must be idempotent."
chr author assisted status --session <session-handle>
chr author assisted finalize --session <session-handle> --target-kind spec --target-name "billing sync spec"
```

The current assisted commands use explicit adapter inputs for deterministic
local behavior.

The legacy quiz-to-draft command remains available for older authoring sessions:

```sh
chr author promote quiz-to-draft --session <session-id> --quiz <quiz-path>
```

## Daemon

Run local foreground coordination:

```sh
chr daemon status
chr daemon start --max-iterations 1
chr daemon stop
```

## Notify

Inspect notification configuration:

```sh
chr notify status
```

Preview the Telegram setup-check payload:

```sh
chr notify telegram test --dry-run
```

Send the Telegram setup-check message:

```sh
chr notify telegram test
```

The dry-run command does not contact Telegram. Non-dry-run dispatch reads the
bot token from the configured environment variable and records a notification
audit event.

Preview Telegram update parsing from a fixture:

```sh
chr notify telegram poll --fixture updates.json --dry-run
```

Persist accepted and rejected remote command handoff records from a fixture:

```sh
chr notify telegram poll --fixture updates.json
```

## Proving

Run direct proving-ground workflows against controlled objectives:

```sh
chr proving validate --objective .chr/proving/objectives/TODO-1-fix-task-id-reuse.md
chr proving run --objective .chr/proving/objectives/TODO-1-fix-task-id-reuse.md --dry-run
chr proving ralph --objective .chr/proving/objectives/TODO-1-fix-task-id-reuse.md --max-attempts 3
```

Proving commands are for sandbox proofing and validation, not the normal ticket
execution path.
