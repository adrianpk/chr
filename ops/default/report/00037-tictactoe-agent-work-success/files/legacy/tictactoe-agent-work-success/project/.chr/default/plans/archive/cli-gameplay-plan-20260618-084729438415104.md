# CLI Gameplay Implementation Plan

## High-level implementation strategy

Close the CLI gameplay gap in the existing Go seed without changing the project shape. The repository already has `go.mod`, `cmd/tictactoe/main.go`, `internal/game/game.go`, and `internal/game/game_test.go`; do not create a new module, alternate command, persistence layer, UI framework, or external dependency.

Workspace decision discovery found no ADR, RFC, decision-log, or engineering-principles files. The binding constraints are the project agent protocol, `.agents/CONVENTIONS.md`, and curated Chryso context: keep rules in `internal/game`, keep process I/O in `cmd/tictactoe`, use only the Go standard library, reject invalid moves without advancing the turn, and exclude replay from the first useful version.

Implement from the domain outward: complete board outcome rules, add a small game-state transition layer, add CLI rendering, wire the interactive loop, then harden tests and final validation.

## Slice decomposition

### S01 - Game Outcome Rules

- slice identifier: `S01`
- title: Game outcome rules
- objective: Complete board-level win and draw detection in `internal/game`.
- implementation rationale: The CLI loop needs reliable terminal-state detection before turn flow can be safely implemented.
- dependencies: None.
- implementation notes: Implement all row, column, and diagonal win lines in `Board.Winner`; implement `Board.Full`; keep board logic independent from stdin/stdout; preserve standard-library-only tests.
- acceptance criteria: All eight win lines are detected; no winner is reported for incomplete or mixed boards; full boards are detected; non-full boards are not detected as full; `go test ./...` passes.
- estimated execution complexity: Low.
- associated tasks: `test(game): cover board winners and full-board detection`; `feat(game): implement winner and full detection`.
- ticket metadata: `cli-gameplay-s01-game-outcomes`, labels `case:cli-gameplay`, `area:internal/game`, `type:implementation`, priority `P1`.
- branch metadata: base `dev`, branch `feature/cli-gameplay/s01-game-outcomes`, target `dev`.
- PR expectations: One focused PR covering only board outcome logic and tests; review should verify all win lines and draw prerequisites.

### S02 - Move State Transitions

- slice identifier: `S02`
- title: Move state transitions
- objective: Add a domain-level game state that tracks turn order and applies valid moves.
- implementation rationale: Keeping turn advancement and invalid-move behavior in `internal/game` prevents the command loop from owning game rules.
- dependencies: `S01`.
- implementation notes: Introduce a small `Game` or equivalent state type with board, current player, and terminal outcome accessors; start with `X`; alternate turns only after valid non-terminal moves; reject occupied cells, out-of-range indexes, and moves after game over without mutating state.
- acceptance criteria: `X` starts; valid moves alternate `X` and `O`; invalid moves leave the current player unchanged; occupied cells are rejected; win and draw states stop further moves; tests cover state transitions table-first.
- estimated execution complexity: Medium.
- associated tasks: `test(game): cover turn advancement and invalid move state`; `feat(game): add game state move application`.
- ticket metadata: `cli-gameplay-s02-move-state`, labels `case:cli-gameplay`, `area:internal/game`, `type:implementation`, priority `P1`.
- branch metadata: base `dev`, branch `feature/cli-gameplay/s02-move-state`, target `dev`.
- PR expectations: One PR limited to domain state and tests; review should focus on mutation safety, invalid move semantics, and terminal-state handling.

### S03 - CLI Board Rendering

- slice identifier: `S03`
- title: CLI board rendering
- objective: Add deterministic CLI presentation helpers for board display, prompts, invalid input messages, and final result text.
- implementation rationale: Rendering can be tested without a full interactive loop and should remain separate from domain rules.
- dependencies: `S02`.
- implementation notes: Keep rendering helpers in `cmd/tictactoe`; display empty cells as positions `1` through `9`; display occupied cells as `X` or `O`; avoid colors, cursor control, and terminal UI packages; keep text stable enough for CLI-facing tests.
- acceptance criteria: Initial board clearly shows available cells; marked board shows player marks; prompt includes the current player; win and draw result text is clear; rendering tests use only standard library assertions.
- estimated execution complexity: Low.
- associated tasks: `test(cmd): cover board and result rendering`; `feat(cmd): add tic-tac-toe CLI rendering helpers`.
- ticket metadata: `cli-gameplay-s03-cli-rendering`, labels `case:cli-gameplay`, `area:cmd/tictactoe`, `type:implementation`, priority `P2`.
- branch metadata: base `dev`, branch `feature/cli-gameplay/s03-cli-rendering`, target `dev`.
- PR expectations: One PR for presentation helpers only; review should verify that rendering does not leak process I/O into domain code.

### S04 - Interactive Gameplay Loop

- slice identifier: `S04`
- title: Interactive gameplay loop
- objective: Replace the seed message with a complete stdin/stdout two-player game loop.
- implementation rationale: With domain rules and rendering in place, the command can run a full local game while keeping I/O injectable for tests.
- dependencies: `S03`.
- implementation notes: Add a `run(args []string, in io.Reader, out io.Writer, errOut io.Writer) int` style boundary or equivalent; keep `main` thin; preserve help handling; read moves line by line; call `game.ParsePosition`; print recoverable errors for invalid text, out-of-range positions, and occupied cells; print final board and winner or draw before exit.
- acceptance criteria: `tictactoe` runs a full game; `-h`, `--help`, and `help` still print usage; invalid input is visible and does not advance the turn; occupied cells do not advance the turn; wins and draws exit cleanly with status `0`; `go test ./...` passes.
- estimated execution complexity: Medium.
- associated tasks: `feat(cmd): wire interactive gameplay loop`; `test(cmd): cover scripted win, draw, and invalid input flows`.
- ticket metadata: `cli-gameplay-s04-gameplay-loop`, labels `case:cli-gameplay`, `area:cmd/tictactoe`, `type:implementation`, priority `P1`.
- branch metadata: base `dev`, branch `feature/cli-gameplay/s04-gameplay-loop`, target `dev`.
- PR expectations: One PR connecting the command to domain logic; review should focus on turn preservation after invalid input and clean termination.

### S05 - Test Coverage Hardening

- slice identifier: `S05`
- title: Test coverage hardening
- objective: Bring test coverage in line with the requested finished implementation.
- implementation rationale: The final slice verifies that the completed game is covered at rule, parsing, state-transition, and CLI-facing levels without adding tools outside the standard library.
- dependencies: `S04`.
- implementation notes: Expand table-driven tests where gaps remain; add a Go fuzz test for `ParsePosition` if parsing remains a separate function; add `testing/quick` only for a simple stable invariant such as valid parsed positions always mapping to indexes `0` through `8`; do not add mutation testing or third-party assertions.
- acceptance criteria: Rule tests cover all win lines and draw states; state tests cover invalid moves without turn advancement; parse tests cover text, whitespace, range boundaries, and valid positions; CLI-facing tests cover at least one win, one draw, help, invalid input, and occupied-cell recovery; `go test ./...` passes.
- estimated execution complexity: Medium.
- associated tasks: `test(game): add parser fuzz and invariant coverage where useful`; `test(cmd): complete CLI gameplay regression coverage`.
- ticket metadata: `cli-gameplay-s05-test-hardening`, labels `case:cli-gameplay`, `area:test`, `type:test`, priority `P1`.
- branch metadata: base `dev`, branch `feature/cli-gameplay/s05-test-hardening`, target `dev`.
- PR expectations: One PR for coverage gaps only; review should reject brittle text overmatching and any non-standard-library test helpers.

## Slice ordering

1. `S01` completes low-level board outcomes.
2. `S02` builds move lifecycle behavior on top of outcome detection.
3. `S03` adds CLI presentation once state shape is stable.
4. `S04` wires the interactive process boundary.
5. `S05` closes coverage gaps after the final behavior exists.

Default execution is sequential. Do not start later branches from unmerged feature branches unless the previous slice is blocked and the dependency impact is explicitly documented.

## Branch strategy

Use `dev` as the integration branch. Create one branch per slice from the latest `dev` after the prior slice merges. Use deterministic branch names: `feature/cli-gameplay/s01-game-outcomes`, `feature/cli-gameplay/s02-move-state`, `feature/cli-gameplay/s03-cli-rendering`, `feature/cli-gameplay/s04-gameplay-loop`, and `feature/cli-gameplay/s05-test-hardening`.

Keep each branch scoped to its ticket. Do not add dependencies, new commands, persistence, network services, colors, replay, AI opponents, player profiles, or terminal UI packages.

## Pull request strategy

Open one pull request per slice into `dev`. Each PR should include a short summary, validation commands, and any intentionally deferred behavior. Keep review scope narrow: domain PRs should not modify CLI text, and CLI PRs should not change domain semantics unless the ticket explicitly requires it.

## Merge sequencing

Merge in slice order: `S01`, `S02`, `S03`, `S04`, then `S05`. After each merge, update local `dev`, rerun `go test ./...`, and create the next branch from the updated integration branch. Do not batch merge multiple slices unless all individual PRs have passed review and validation.

## Review requirements

Reviewers should verify that game rules remain in `internal/game`, process I/O remains in `cmd/tictactoe`, and all code uses only Go's standard library. Review must check invalid input behavior specifically: invalid text, out-of-range numbers, and occupied cells must be rejected without advancing the turn. Review should also verify all row, column, and diagonal wins, draw detection, final board printing, help behavior, and absence of optional replay or non-goal features.

## Completion validation criteria

The use case is complete when `go test ./...` passes, the command can run a full two-player game from stdin/stdout, the initial board shows positions `1` through `9`, `X` starts, turns alternate only after valid moves, invalid moves are visible and recoverable, occupied cells are rejected without losing the turn, all wins and draws produce a clear final result, and the final board is printed before exit.

Additional validation: run a scripted X win through `go run ./cmd/tictactoe`; run a scripted draw; run a scripted invalid-input flow that proves the same player remains on turn; run `go run ./cmd/tictactoe --help`; run the parser fuzz target with a short fuzz time if `S05` adds one.
